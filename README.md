# mathematical-methodology

A minimal [Lean 4](https://lean-lang.org) implementation of the method in
[`juanmichelini/foundations`](https://github.com/juanmichelini/foundations):
*some mathematical methods can be treated as mathematical objects.*

## What this is for

The thesis describes a method that **humans actually use**: the original repo followed a university
course closely, so we know from experience that people can follow it. It has three levels: what is possible
(terms and computation), how to attempt a proof (search, lemma store), and what is worth
proving (enumerating types, functions and conjectures, then choosing lemmas).

This project formalizes that method in Lean and runs it **end to end, automatically**:
it enumerates, conjectures, proves, and rediscovers what a person following the method would.

**The method is the important part.** Appendix B of the thesis (31 functions and their lemmas)
matters only as *evidence about the method*: if the method, run mechanically, rediscovers the
same functions and lemmas, that supports the claim that it is a mathematical object we can run.
The results are not the goal.

The same holds for Lean. Everything the system generates should be **real Lean**, as the
original's functions were real Haskell: definitions and proofs that Lean itself accepts. But
compiling Appendix B in Lean proves nothing about the method unless it is done **mechanically,
from the method**: generated by the system, not written or fixed by hand. A file that compiles
because someone curated it is worthless as evidence. Where generated output does not compile,
that is a reported failure about the method.

### Parity and parity plus

*Parity* (evidence that the method works; tracked in [#38](https://github.com/juanmichelini/mathematical-methodology/issues/38)): all results of Appendix B match the original, and
the generated functions export to Lean and run there.

*Parity plus*: the proofs the system generates **compile in Lean automatically**, i.e.
mechanically from the method, for any development it proves, not only for files we chose to
commit.

### Where it stands

- **Parity: reached.** The 31 functions of Appendix B, their lemma statements and finished-proof
  counts, and the 64 / 164 candidate counts match the original Haskell, which was run on GHC to
  compare. The 31 functions export to Lean and run (`Generated/AppendixB.lean`).
- **Parity plus: not reached.** The 123 Appendix B lemmas, with the proofs the search found,
  compile in Lean with no axioms (`Generated/AppendixBProofs.lean`). Not yet: the 35-lemma suite
  and chains of `Test.hs`, and a gate that makes a lemma count as proved only if its Lean theorem
  compiles ([#53](https://github.com/juanmichelini/mathematical-methodology/issues/53)). Hand-written
  certificates are not counted (they are not mechanical).
- **Traces**: `lake exe trace` records everything enumerated, conjectured and attempted, not only
  what was proved (not committed).

The committed `Generated/*.lean` files are not hand-written: they are the generator's output
(`lake exe export-lean`), CI regenerates them and fails if they differ, and `lake build` compiles
them. That is what makes them evidence; a hand-edited file would not be.

### Open questions

- The core uses de Bruijn indices (smaller trusted base, soundness proofs) at the cost of
  human-readability and one-to-one correspondence with the thesis: [#36](https://github.com/juanmichelini/mathematical-methodology/issues/36).
- How much the port has drifted from a method people can follow: [#37](https://github.com/juanmichelini/mathematical-methodology/issues/37).
- Whether the end state is a general engine for new data types and functions, beyond the
  thesis' examples, which would make the exporter's generality central.

The method has three levels, and so does the code:

| Level | Question | Where | Trusted |
|---|---|---|---|
| Operational | what is possible? | `MathematicalMethodology/Operational/` | yes |
| Tactical | how do we attempt it? | `MathematicalMethodology/Tactical/` | `Cert.check` only |
| Strategic | what is worth proving? | `MathematicalMethodology/Strategic/` (enumeration, conjectures, lemma search) | no |

Proofs are *certificates* (`Cert`) that a small checker re-verifies. The headline
example, in `Examples/Lists.lean`, checks `rev (rev xs) = xs` together with the lemmas
it needs (`append_nil`, `append_assoc`, `rev_append`).

## Build

```
lake build                            # builds and runs the #guard tests
lake exe results > results/report.md  # regenerate the committed report
lake exe trace [dir] [first|all]      # write traces of everything enumerated/conjectured/attempted (not committed)
```

Tests are `#guard` checks inside the Lean files, so a successful build means they pass.
[`results/report.md`](results/report.md) records what the checker accepts and rejects;
CI regenerates it and fails if the committed copy is stale.

## Status

The checker is **proved sound**: `Cert.check_sound`
(`Semantics/CheckSound.lean`) says that if a certificate is accepted then the statement
holds, as a `Conv` equation (delta, beta, case), for every substitution of *values*
for its variables.  The theorem is conditional on three explicit assumptions about the
checker's context (definitions are closed, declared function signatures are right, data
type names are unique); `Examples/ListsSound.lean` proves them for the list example,
which gives `development_valid` and `revRev_valid`.  Not proved: that the defined
functions are total in general (it is an assumption per development), termination
of computation, or anything about the untrusted search and strategy levels.
See [`docs/ROADMAP.md`](docs/ROADMAP.md).
